# Landscape: agent identity, delegation and audit trails

As of 9 November 2026. Confidence tags: **[Certain]** read on a primary page, **[Likely]** inferred from primary pages, **[Guessing]** thin or secondary evidence.

"Cross-system attribution" below means one record that says: agent A (model M, version V) acted for user B, approved by C, through tools D and E.

## Correction after reading Tracekit's source (9 Nov 2026, later the same day)

The verdict below listed three open gaps. A read of Tracekit's repository at commit `4c95b3c` shows two of them are already covered there, so the remaining gap is smaller than this file first said. The code was read, not run.

- **Identity from verified tokens: covered (marked experimental).** `register_run` accepts `principal_token`, checks it against configured OIDC issuers and records `principal_attested: true`; approvers are authenticated identities, self-approval is refused on a configured signer, and the `approval` record carries the approver's person id ([docs/identity.md](https://github.com/Cygnux-Labs/Tracekit/blob/main/docs/identity.md), [docs/approvals.md](https://github.com/Cygnux-Labs/Tracekit/blob/main/docs/approvals.md)). **[Certain]** that the docs and schema say this.
- **Model version: covered, on a separate record.** Model calls are recorded as `model.exchange` events with provider and the model id the provider returned ([tracekit/autotrace.py](https://github.com/Cygnux-Labs/Tracekit/blob/main/tracekit/autotrace.py)). It sits in the same run as the tool call rather than on the tool call record. **[Certain]**
- **Still open, small:** the viewer's run search filters by run, agent, tenant, time and verdict, not by principal ([docs/viewer.md](https://github.com/Cygnux-Labs/Tracekit/blob/main/docs/viewer.md)), so "what did this agent do for user X today" is not a direct query. **[Likely]** No shared standard across the twenty formats also still holds.

Net: there is no room for a new accountability record library. The honest options are a demo built on Tracekit, a small contribution to it, or neither.

## Verdict (original, see correction above)

**The gap as originally framed is closed.** "A small open-source layer that records who acted, on whose behalf, and who approved, via a LangGraph callback and an MCP proxy, signed and append-only" already exists several times over. [Tracekit](https://github.com/Cygnux-Labs/Tracekit) (MIT, about 600 stars, v1.6.0) ships stable MCP and LangChain/LangGraph integrations, signed hash-chained records, approvals bound to exact arguments, and a record format with `principal`, `principal_attested`, `tenant`, `parent_run` and approver fields ([Format v2](https://github.com/Cygnux-Labs/Tracekit/wiki/Format-v2)). [Signet](https://github.com/Prismer-AI/signet), [Agent Receipts](https://github.com/agent-receipts/obsigna), [Provenrail](https://github.com/pofky/provenrail) and [Agent Passport System](https://github.com/aeoess/agent-passport-system) cover overlapping ground, and a [curated list](https://github.com/systempromptio/awesome-ai-agent-governance) names roughly twenty more. Another signed receipt library would be the twenty-first, and none of the existing ones except Tracekit has traction. What is still open is narrower and less glamorous: (1) nothing joins the two halves of the story, since identity vendors log token issuance and approval but explicitly not tool calls, while receipt libraries log tool calls but mostly take identity as an app-supplied string; (2) model name and version is not a first-class field in any record format I could verify; (3) there is no standard schema, with MCP audit absent from the spec and its roadmap, and the OpenTelemetry GenAI conventions still unstable. A defensible project is therefore a thin, OTel-native **join record** that lifts principal, actor and approver from verified tokens and carries the correlation keys needed to line up with Okta, Auth0 or Entra logs. It is a schema and interop play, not a cryptography play. Whether that is worth building, versus contributing those fields to Tracekit, is a real question (see the end).

## What is and is not covered

Covered, and not worth rebuilding:

- Signed, hash-chained per-call receipts (Tracekit, Signet, Agent Receipts, Provenrail and many more).
- MCP proxy capture and LangChain/LangGraph callback capture (Tracekit, Signet).
- Approval bound to exact arguments (Tracekit).
- Narrowing delegation chains (Signet, Agent Passport System, and in tokens via RFC 8693 and ID-JAG).
- Agent identity and "who authorized this agent" at the token layer (Okta, Auth0, WorkOS, Descope, Entra).

Still open:

1. **The join.** Every identity vendor stops at token issuance or approval and tells you to correlate with application traces yourself (Auth0 and WorkOS say so in as many words). Every receipt library starts at the tool call. No open component takes the verified token claims (`sub`, `act`, ID-JAG, CIBA approval reference) and stamps them on the tool call record together with the IDs needed to look the same event up in the IdP log.
2. **Model version as a first-class field.** "Which model version made the call" is answerable only in Provenrail (name, zero adoption) and in ad hoc trace metadata.
3. **A standard.** No MCP audit schema, no stable OTel attributes for principal or approver that I could verify. Twenty incompatible receipt formats is itself the evidence.
4. **Attested versus asserted identity.** Only Tracekit distinguishes them. Most records carry a user id string the app chose.

## What this means for the project

- Do not compete on signatures, chains, witnesses or policy enforcement. That race is crowded and Tracekit is ahead.
- If the project goes ahead, its only honest differentiator is the join record: identity lifted from tokens, model version, IdP correlation keys, OTel as the primary export. That is roughly a few hundred lines plus a schema.
- The cheaper alternative is to propose those fields to Tracekit and to the OTel GenAI conventions, and build only the demo and viewer on top. That gets the discovery conversations in step 2e without maintaining a twenty-first format.
